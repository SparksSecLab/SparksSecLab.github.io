01 // INCIDENT

Websites Will Not Load

A simulated Finance user, Sarah Foster, reported that websites would not open on WIN10LAB. The exercise focused on Tier 1 investigation, customer communication, and identifying when additional support access was needed.

Outcome: Escalation documentation prepared. Ticket reassignment and service restoration were not verified.

02 // ENVIRONMENT

Windows Domain and Ticketing Lab

WORKSTATION

WIN10LAB · Windows 10

DOMAIN SERVICES

DC01 · Active Directory and DNS

TICKETING

osTicket and Mailpit · Docker on Ubuntu

Before the fault was introduced, website access and access to the Finance share were confirmed. A manual proxy pointing to 127.0.0.1:65534 was enabled for scenario setup. Knowledge of that setup was kept separate from the evidence gathered in the technician role.

03 // INITIAL ASSESSMENT

Establish Location, Scope, and Impact

I asked whether Sarah was in the office or remote, whether coworkers were affected, and whether she could access shared drives.

In the role-play, Sarah reported that she was in the office, a coworker could browse normally, and Finance files remained accessible. This narrowed the reported scope to one workstation without establishing that all internet connectivity was unavailable.

04 // WORKSTATION CHECKS

Review Network Configuration

I used ipconfig /all to review the workstation configuration.

IP ADDRESS / MASK

192.168.100.11 / 255.255.255.0

DEFAULT GATEWAY

192.168.100.2

DNS SERVER

192.168.100.10

These values matched the intended lab settings; that alone did not prove connectivity. DHCP was disabled because the address was static. IP routing and WINS proxy being disabled were not faults for this workstation.

05 // DNS FINDING

Record an Unresolved Timeout

nslookup google.com on WIN10LAB returned a DNS request timeout while querying 192.168.100.10. The “Server: Unknown” label alone was not evidence of failure; the missing response was the relevant finding.

The timeout remained unresolved. A separate setup check showed that DC01 could resolve a name locally, but that did not prove that WIN10LAB could receive DNS responses. Server administration was outside the subsequent Tier 1 workflow.

06 // BROWSER EVIDENCE

Request the Exact Error

I asked Sarah for a screenshot and offered to explain how to take one. In the simulated customer response, the error was ERR_PROXY_CONNECTION_FAILED, with a message about the proxy server or its address.

The exact error code came from the role-play and was not verified from an uploaded browser screenshot. It supported checking the user’s proxy settings against the approved configuration.

The user could not access workstation settings, and no approved technician access method was established for this exercise. I prepared escalation to Tier 2/Desktop Support rather than bypassing the restriction.

The proxy issue remained a hypothesis in the technician workflow. The unresolved DNS timeout was retained as a separate finding.

08 // CUSTOMER COMMUNICATION

Explain the Next Step

Sarah, I'm going to escalate your issue to a tier 2 technician who has access to investigate further.

I removed an earlier promise that Sarah would hear back “shortly” because no response timeframe had been confirmed.

09 // PREPARED HANDOFF

Give Tier 2 Useful Evidence

Issue: Sarah Foster reports that websites will not load on WIN10LAB.

Scope: In-office user; coworker reportedly unaffected; Finance share reportedly accessible.

Checks: IPv4 192.168.100.11/24, gateway 192.168.100.2, DNS 192.168.100.10. DNS lookup timed out. Simulated browser report: ERR_PROXY_CONNECTION_FAILED.

Assessment: Suspected proxy configuration issue. Proxy settings not verified during Tier 1 investigation. DNS timeout remains unresolved.

Escalation reason: User cannot access settings; no authorized Tier 1 access method established.

Requested next steps: Inspect proxy settings against the approved baseline, investigate the DNS timeout as needed, and verify website and Finance share access after remediation.

Ticket handling: Keep open and route according to the support process. This write-up records the prepared handoff, not a confirmed reassignment or resolution.

10 // LESSONS LEARNED

Evidence and Scope Before Changes

DISTINGUISH SYMPTOMS

A website error does not prove a complete internet outage.

DOCUMENT UNCERTAINTY

Separate observed results from suspected causes and retain unresolved findings.

RESPECT ACCESS LIMITS

Use approved support access or escalate with evidence.

SET EXPECTATIONS

Explain escalation without promising an unconfirmed response time.
